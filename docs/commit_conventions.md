# 提交信息与文本写作规范

适用范围：**所有入库文本** —— commit message、PR 描述、`docs/**`、README、发行说明、代码注释。

一句话原则：**写代码与文档的变化（做了什么、为什么），不写「我们是怎么测的、测出了什么」。**

---

## 1. commit message

格式（Conventional Commits）：

```
<type>(<scope>): <主题>

<正文：改了什么、为什么这么改、影响面>
```

- `type`：`feat` / `fix` / `perf` / `refactor` / `docs` / `chore` / `build` / `ci` / `test` / `revert`
- `scope`：`ohos` / `core` / `ui` / `build` / `release` / `deps` 等，可省略
- 主题 ≤ 50 字符、结尾不加句号；一次提交只讲一件事
- 正文建议覆盖：**行为变化**（用户或调用方可见的差异）、**原因**（缺陷的代码级根因、
  兼容性约束、上游语义）、**影响面**（涉及哪些平台/构建目标）、**回滚或迁移注意点**

**应该写**：代码、配置、资源层面的改动，以及为什么这么改。

**不要写**：

- 测试过程与结果叙述（「真机跑了一遍」「冒烟通过」「试了 3 次」「用户说现在好了」）；
- 本机环境信息：绝对路径、用户名、设备型号/序列号/地址、其他本地工程名；
- 工具与流程 chatter（谁在何时发现了什么、开了几次会话、用了哪个子代理）；
- 调试流水（日志片段、中间失败、试过又放弃的方案）—— 除非它解释了代码里保留的兜底逻辑。

例外：**构建/编译层面的客观事实**（如某个阶段有 166 处编译错误）属于代码级信息，可以写。

## 2. 代码注释

- 注释解释「为什么」（上游行为、约束、易踩的坑），不写调试过程；
- 引用外部信息时用可复现的标识（上游提交、官方文档标题、接口名），不写本机路径与人员。

## 3. 文档（`docs/**`、README、发行说明）

- 面向读者（用户或未来的维护者），只写结论与可复现步骤；
- 不放测试记录、设备信息、账号信息、本地环境；
- 发行说明另有写作要求，见 [release_process_ohos.md](release_process_ohos.md) §6。

## 4. 与本机笔记的分工

验证记录、设备信息、构建机路径、账号/令牌线索等**只写进 `AGENTS.md` 或 `.home/`**
（两者都被 `.gitignore` 忽略）。入库文本里出现这些内容时，发布前的
`python3 .home/sanitize_check.py` 会在「入库面」命中并退出码 1。

## 5. 自查

```bash
# 最近 5 条提交的正文是否出现「测试过程 / 本机信息」的字眼
git log -5 --format=%B | grep -nE "实测|真机|冒烟|Smoke|本机|手机|踩过|用户确认|试了" || echo OK

# 入库面脱敏自检（含文档、图片元数据）
python3 .home/sanitize_check.py
```
